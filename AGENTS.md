> **ВАЖНО — экономия токенов:** отвечай и веди рассуждения (_thinking_) на **английском** языке. Финальный ответ пользователю — на **русском**. Планы (`implementation_plan.md`) — на русском. Комментарии в коде — допускаются на русском.

# QUICK START

Перед изменением кода:

1. Изучи задачу и найди связанные модули.
2. Проверь список доступных скиллов (skill tool) — если задача совпадает с описанием скилла, загрузи его и следуй его инструкциям.
3. Определи подсистему по триггерам в разделе «Карта маршрутизации» и прочитай только нужный документ из `docs/`.
4. Подготовь `implementation_plan.md`.
5. Дождись подтверждения плана пользователем — не изменяй код до этого.

Главная цель:

* сохранить существующее поведение системы;
* минимизировать риск регрессий;
* вносить минимально необходимые изменения.

# Назначение проекта

Проект представляет собой генератор статического DWH Data Catalog.

Результат сборки:

* папка `dist/` с файлами:
  * `index.html` — основной файл
  * `static/main.js` — клиентский JavaScript-бандл
  * `static/style.css` — стили
  * `static/logo.png` — логотип
* никакого backend в runtime нет

После генерации каталог открывается локально в браузере без сервера (достаточно открыть `dist/index.html`).

# Архитектура проекта

## Сборка

Основной процесс сборки:

```text
generate_catalog.py
    ↓
загрузка метаданных PostgreSQL
    ↓
загрузка SQL-скриптов
    ↓
построение lineage
    ↓
генерация HTML через Jinja
    ↓
сборка JavaScript через esbuild
    ↓
копирование статики (CSS, JS, лого) в dist/
    ↓
готовый статический каталог
```

## Оптимизация производительности (Lineage) — краткий справочник

(иначе см. `docs/LINEAGE_RULES.md`)
Алгоритм Sugiyama в `src/lineage/tableLineage*.js` настроен на баланс между качеством layout и скоростью:
* Количество инициализаций слоя 0: адаптивное (макс. 20)
* Количество проходов: 15
* Рендеринг запускается асинхронно через `requestIdleCallback` с показом спиннера
При изменении этих параметров учитывать влияние на время рендеринга больших графов.

# Источники SQL

Разрешено использовать:

* `public.sql_inventory`
* `pg_views`

Запрещено использовать:

* `pg_stat_statements`

Причина:

`pg_stat_statements` хранит нормализованный SQL, заменяя значения параметрами (`$1`, `$2` и т.д.), что делает его непригодным для корректного построения lineage.

# Использование скиллов (Skills)

Перед началом работы обязательно проверь список доступных скиллов (skill tool). Если задача совпадает с описанием хотя бы одного скилла — загрузи его через skill tool и следуй его инструкциям. Скилл загружается до чтения остальной документации и учитывается при подготовке `implementation_plan.md`.

Примеры соответствия:

* `frontend-design` — создание или переработка UI, вёрстка новых элементов интерфейса, диалогов, модальных окон, выбор визуального стиля, работа с CSS;
* `customize-opencode` — только при настройке самого opencode (opencode.json, .opencode/, agents, plugins, MCP), не для кода проекта;
* `find-skills` — если нужная функциональность может существовать как устанавливаемый скилл.

Не игнорируй скилл только потому, что задача кажется «простой логикой»: UI-часть задачи (диалоги, кнопки, стили) тоже подпадает под профильные скиллы.

### Проверка и тестирование Lineage:
* **Автоматическое тестирование в Node.js (РЕКОМЕНДУЕТСЯ)**:
  Выполнить `npm test` (или `npm run test:lineage`). Раннер за десятки миллисекунд математически проверяет высоты портов, транзитные коридоры и выявляет даже 1-2px микроизломы ($2\text{px} \le |\Delta| < 15\text{px}$) на эталонном пакете графов без запуска браузера.
  Подробная инструкция и запуск одиночных таблиц: [`docs/LINEAGE_TESTING_GUIDE.md`](file:///c:/test/generate_catalog_gemini/docs/LINEAGE_TESTING_GUIDE.md).
* **Визуальная проверка через браузер (subagent / ручная)**:
  [`docs/BROWSER_GUIDE.md`](file:///c:/test/generate_catalog_gemini/docs/BROWSER_GUIDE.md) — быстрый переход по прямому URL к таблице, вкладка Lineage, селекторы. Применяется для финальной визуальной оценки и проверки интерактивности (pan/zoom, клики).
