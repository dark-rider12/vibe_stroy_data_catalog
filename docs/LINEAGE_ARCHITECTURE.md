# LINEAGE_ARCHITECTURE.md

## Назначение

Документ описывает архитектуру подсистемы Lineage.

Перед изменением алгоритмов построения графа, маршрутизации связей или визуализации необходимо ознакомиться с этим документом.

Подробности маршрутизации рёбер описаны отдельно в:

* LINEAGE_ROUTING_ALGORITHM.md

---

# Общая схема

Построение lineage выполняется в несколько этапов:

```text
SQL Sources
    ↓
SQL Parsing
    ↓
Dependency Extraction
    ↓
Graph Building
    ↓
Layer Assignment
    ↓
Layout Optimization
    ↓
Edge Routing
    ↓
HTML Rendering
```

Каждый этап имеет собственную ответственность.

---

# Основные подсистемы

## SQL Parsing

Назначение:

Преобразование SQL-кода в структурированное представление.

Результат:

* таблицы
* колонки
* алиасы
* CTE
* JOIN
* UNION
* подзапросы

На этом этапе граф ещё не строится.

---

## Dependency Extraction

Назначение:

Определение зависимостей между объектами.

Результат:

```text
source_table
    ->
target_table
```

и

```text
source_column
    ->
target_column
```

Формируются связи для будущего графа.

---

## Graph Building

Назначение:

Построение внутреннего графа lineage.

Результат:

Набор:

* Nodes
* Edges

Граф является основным источником истины.

Все представления строятся только на его основе.

---

# Основные сущности

## Node

Узел графа.

Представляет:

* таблицу
* view
* промежуточный объект

Хранит:

* идентификатор
* имя
* слой
* координаты
* связи

---

## Edge

Связь между узлами.

Хранит:

* источник
* приемник
* параметры маршрутизации

---

## Layer

Вертикальный уровень графа.

Используется для расположения объектов слева направо.

Пример:

```text
Layer 0
    ods

Layer 1
    dds

Layer 2
    dm
```

---

## Port

Точка подключения ребра к узлу.

Используется для:

* fan-in
* fan-out
* группировки связей

---

## Dummy Node

Виртуальный узел.

Используется только внутри layout-алгоритма.

Назначение:

* поддержка длинных связей
* транзит через несколько слоев
* резервирование пространства

Не отображается пользователю.

---

# Типы графов

Система поддерживает несколько представлений одного и того же графа.

---

## Table Lineage

Уровень таблиц.

Пример:

```text
ods.orders
    →
dds.orders
    →
dm.sales
```

### Структура модулей Table Lineage

Реализация Table Lineage разделена на специализированные модули:

* `tableLineage.js` — фасад и оркестрация: сборка контейнеров DOM, pan/zoom, toolbar, DFS-сбор данных, последовательный запуск этапов;
* `tableLineageConstants.js` — константы визуализации, отступы, лимиты проходов Sugiyama, иконки;
* `tableLineageHighlight.js` — интерактивность: клики по узлам/рёбрам, BFS-обходы графа, подсветка и очистка выделения;
* `tableLineageSugiyama.js` — топология и распределение по слоям: создание dummy-узлов (vnodes), барицентр, медиана, sifting, подсчёт пересечений через Fenwick BIT (O(m log m));
* `tableLineageLayout.js` — физический layout узлов: выравнивание колонок под родителей, разрешение коллизий и upward compaction (Phase 2), изолированные пары (2.3), прямое верхнее входящее ребро (Rule 18, включая раскрутку транзитных цепочек TargetToTransitSource), адаптивное расширение зазоров между слоями;
* `tableLineageEdges.js` — расчёт портов, сквозной прямой транзит (Rule 15 для всех цепочек с выравниванием микроизломов и поиском чистой полосы findFreeTransitY), бесконфликтные треки (Rule 11), fan-in (Rule 12), fan-out (Rule 12b), арочные дуги (R=5) и генерация SVG-путей.

---

## Column Lineage

Уровень колонок.

Пример:

```text
ods.orders.amount
    →
dds.orders.amount
    →
dm.sales.amount
```

Содержит два режима отображения:

* **Фокусный режим**: отображаются только колонки, участвующие в lineage-цепочке выбранной колонки
* **Полный режим**: отображаются все колонки всех таблиц в графе

### Структура модулей Column Lineage

Реализация Column Lineage разделена на специализированные модули. Изменения следует вносить в модуль, отвечающий за нужную часть поведения:

* `columnLineage.js` — оркестрация: инициализация, pan/zoom, toolbar и обработка событий;
* `columnLineageGraph.js` — построение графа и трассировка lineage;
* `columnLineageCards.js` — генерация карточек;
* `columnLineageEdges.js` — маршрутизация и SVG-отрисовка рёбер;
* `columnLineageLayout.js` — позиционирование карточек;
* `columnLineageFocus.js` — фокусный режим;
* `columnLineageConstants.js` — константы визуализации.

### Алгоритм выравнивания Column Lineage:

1. **Определение основной цепочки**: самый длинный путь через выбранную колонку (включая родителей и потомков)
2. **Смещение ответвлений**: колонки, не входящие в основную цепочку, смещаются вниз на **150px** от прямой линии
3. **Выравнивание в слое**:
   - Если `count(текущий_слой) > count(следующий_слой)` → таблицы **касаются** (зазор = 0px)
   - Иначе → таблицы имеют **зазор 20px** для прямого хода рёбер
4. **Применение для обоих режимов**: правило работает и в фокусном, и в полном режиме

# Layout Pipeline

После построения графа начинается вычисление координат.

Этапы:

```text
Graph
    ↓
Layer Assignment
    ↓
Node Ordering
    ↓
Collision Resolution
    ↓
Edge Routing
    ↓
Render
```

---

## Layer Assignment

Определяет:

в каком слое должен находиться каждый узел.

Главная цель:

обеспечить движение данных слева направо.

---

## Node Ordering

Определяет порядок узлов внутри слоя.

Главная цель:

минимизация пересечений связей.

Порядок вычисляется алгоритмом Sugiyama:
медиана/барицентр (15 проходов forward/backward),
затем 2 прохода sifting; подсчёт пересечений — через
Fenwick (BIT), O(m log m). Подробности см. в:

LINEAGE_ROUTING_ALGORITHM.md

---

## Collision Resolution

Устраняет наложения объектов.

Задачи:

* сохранить читаемость
* создать место для связей
* обеспечить корректную работу routing

**Важно для Column Lineage:** финальный collision pass выполняется после всех этапов позиционирования (выравнивание основной цепочки, смещение ответвлений). Все позиции карточек снимаются **до** начала цикла (`getBoundingClientRect` не обновляется внутри JS-цикла), нижняя граница отслеживается вручную через `trackedBottom`. Карточки сдвигаются только вниз. Подробности см. в `LINEAGE_ROUTING_ALGORITHM.md`, правило 14.

**Table Lineage — Phase 2 (`renderLineageCore`):**

* **2.1 Alignment** — потомок выравнивается под выбранного родителя через `marginTop`, сдвиг клампится до `±2*BUNDLE_SPACING` (±16px).
* **2.2 Collision + Upward compaction** — раздвижка перекрытий вниз и схлопывание пустот вверх (не выше исходной стековой позиции узла).
* **2.3 Straight Isolated Pairs** — источники первого слоя с единственным реальным потомком, у которого единственный родитель, сдвигаются под порт потомка ради прямого ребра; сдвиг применяется только при сохранении зазоров `minGap` к соседям своей колонки. Если сдвиг источника блокируется зазорами, применяется fallback: сдвигается потомок в противоположную сторону с той же проверкой зазоров (правило 16).

Проходы расположены между Phase 2 и «Фазой 3» (`tableLineage.js:869-914`); порядок узлов (Sugiyama), порты и треки не затрагиваются. Подробности — в `LINEAGE_ROUTING_ALGORITHM.md`, правила 15 и 16.

---

## Edge Routing

Прокладывает маршруты между узлами.

Задачи:

* избежать пересечений через узлы
* сохранить читаемость
* минимизировать визуальный шум

**Транзитные рёбра (Column Lineage):** рёбра, перепрыгивающие через один или несколько слоёв (`|srcDepth − tgtDepth| > 1`), огибают карточки промежуточных слоёв. Вертикальный сегмент ребра сдвигается влево от промежуточной карточки на `bypassOffset`, который зависит от номера ребра в группе — это гарантирует уникальность X-координат и отсутствие наложений. Подробности см. в `LINEAGE_ROUTING_ALGORITHM.md`, правило 13.

**Прямой транзит (Table Lineage):** длинные цепочки `реальный узел → vnode → … → реальный узел` держат горизонтальную полосу на высоте источника. Чтобы транзит не проходил сквозь реальные таблицы промежуточных колонок, полоса выбирается на ближайшей свободной высоте (`findFreeTransitY`, «чистая полоса»). Подробности см. в `LINEAGE_ROUTING_ALGORITHM.md`, правило 15.

**Выравнивание «магнитных» рёбер (Table Lineage, Фаза 3):** УДАЛЕНО (2026-09). Сдвиг таблиц через `marginTop` для коротких рёбер (`|diff| < 15`) давал каскадные смещения во flex-потоке, откатывался вторым проходом цикла стабилизации и ломал уже прямые рёбра. Блоки `alignMoves`/`bothBundledMoves`/`childFallbacks`/`preservePairs` исключены; короткие S-кривые остаются естественными. Прямые рёбра выравниваются механизмом 2.3/16 (изолированные пары) и правилом 15 (цепочки с `diff ≥ 15`).

**Прямое верхнее входящее ребро (Table Lineage, Фаза 3, правило 18):** верхнее входящее ребро каждой реальной таблицы (ребро на верхнем порту) выравнивается горизонтально через `marginTop` с защитой зазоров (`shiftWithGap`):
- Источник Слоя 0 (без входящих рёбер) с одним исходящим ребром сдвигается первым (fallback — цель).
- Промежуточный источник (имеющий родителей) **никогда не сдвигается как источник** — вместо этого сдвигается только цель (`TargetToSource`), сохраняя входящие горизонтали источника нетронутыми.
- У фан-аутов (источник с несколькими детьми) сдвигается исключительно цель; откат на сдвиг источника исключён во избежание деформации связей к родителю и другим детям.
- Для первой карточки слоя разрешён отрицательный `marginTop` до `-32px` для подтягивания вверх к родителю.
- Строго прямые рёбра ($|\Delta| < 0.5$) фиксируются в `shiftedCards`.
- Верхние рёбра из vnode-цепочек не трогаются (их выравнивает Straight Transit/правило 15).
Проход выполняется до `finalPorts`; после сдвигов rects перечитываются. Отладка и мониторинг сдвигов ведутся через модуль `tableLineageDebug.js` (`window.__LINEAGE_DEBUG__`).

Подробности реализации см. в:

LINEAGE_ROUTING_ALGORITHM.md

# Источник истины

Критически важно:

Существует только один источник истины.

Им является внутренний граф зависимостей.

Запрещено:

* хранить отдельные версии графа для разных режимов
* вручную синхронизировать разные представления
* дублировать зависимости

Все режимы должны строиться из одного графа.

# Производительность

При работе с lineage избегать:

* полного пересчета графа без необходимости
* дублирования структур данных
* повторного обхода графа в циклах
* вычисления layout при каждом UI-событии

Предпочтительно:

* кеширование
* переиспользование вычисленных структур
* локальные обновления
