# SMART_EXECUTION_HELPER.md

## Назначение

Документ описывает подсистему **Smart Execution Helper (Smart Rebuild Flow)** на вкладке **Table Lineage**.

Функционал предоставляет дата-инженерам и аналитикам возможность прямо из интерактивного графа Table Lineage:
1. Отметить таблицы ODS-слоя, в которые поступили новые данные (`+ New Data`).
2. Мгновенно визуализировать затронутое поддерево потомков (downstream impact).
3. Последовательно слева направо (downstream) выбрать витрины и таблицы, требующие пересчёта.
4. Автоматически выявить узлы, пересборка которых заблокирована из-за отсутствия скрипта трансформации в `sql_inventory`.
5. Сгенерировать упорядоченный SQL-скрипт, готовый к запуску в DWH.

# 1. Пользовательский интерфейс и сценарии

## 1.1. Активация режима пересборки на таблицах любого слоя
* **Чистый исходный граф:** по умолчанию на карточках таблиц никаких бейджей не отображается (в том числе при наведении курсора или выделении таблицы кликом), внешний вид графа остаётся чистым и стандартным.
* **Появление по правому клику (ПКМ):** при нажатии правой кнопкой мыши по карточке любой таблицы над ней плавно проявляется кнопка запуска пересборки:
  * Для таблиц слоя **ODS**: янтарный бейдж `+ New Data`;
  * Для таблиц промежуточных слоёв (**DDS**, **DM** и др.): индиго-бейдж `+ Rebuild`.
  * Повторный клик ПКМ или клик мимо карточки скрывает неактивированный значок.
* **Обычный клик (ЛКМ):** клик левой кнопкой мыши в тело карточки выполняет стандартное выделение таблицы и подсветку её связей (`handleLineageClick`).
* **Клик по значку активации:**
  * **ODS (`+ New Data`)**: переводит кнопку в активный режим `New Data ✕` и активирует режим пересборки (`rebuild-flow-active`). Сама ODS-таблица выступает внешним источником (не требует скрипта в SQL).
  * **Не-ODS (`+ Rebuild`)**: переводит кнопку в `Шаг 1: Rebuild ✕` и сразу включает данную таблицу первым шагом в очередь выполнения SQL, делая её дочерние таблицы доступными для выбора (`+ Выбрать`).
  * Повторный правый клик или клик по крестику `✕` снимает статус.
* **Мультивыбор на поблекших таблицах:** когда режим пересборки уже активен, несвязанные таблицы приглушаются, но сохраняют возможность взаимодействия. Пользователь может кликнуть **ПКМ по поблекшей таблице** — она возвращает полную яркость и отображает значок активации (`+ New Data` или `+ Rebuild`), позволяя объединять независимые поддеревья пересборки.
* **Снятие статуса:** повторный клик по кнопке с крестиком `✕`, повторный ПКМ по источнику или клик по кнопке «Сбросить» в нижней панели отключает режим.

## 1.2. Визуализация графа и сохранение связей
При активации хотя бы одного источника:
* **Приглушение несвязанных элементов:** все узлы и рёбра, не входящие в downstream-поддерево активных источников, блекнут (`opacity: 0.18` для узлов, `opacity: 0.08` для рёбер).
* **Сохранение видимости дерева потомков:** все рёбра внутри цепочки потомков (`.ln-edge-rebuild-tree`) остаются полностью видимыми (`opacity: 0.9`, нейтральный цвет `#94A3B8`, толщина 2px), наглядно показывая инженеру все возможные пути распространения данных.
* **Индикация выбранных шагов:** рёбра между подтверждёнными шагами пересборки окрашиваются в ярко-изумрудный цвет (`#10B981`, толщина 2.8px со свечением).

## 1.3. Статусы карточек и верхние pill-бейджи
В режиме пересборки карточки-потомки **не изменяются в размерах**. Все управляющие элементы вынесены на верхнюю правую грань карточки (`position: absolute; top: -12px; right: 8px;`) в едином стиле компактных pill-бейджей:

| Статус | CSS-класс | Визуальное отображение (бейдж вверху справа) | Поведение |
|---|---|---|---|
| **Готов к выбору** | `.ln-rebuild-eligible` | Изумрудный pill-бейдж `+ Выбрать` с мини-чекбоксом | Доступен для клика. Все входящие родители в активной ветке уже удовлетворены |
| **Выбран** | `.ln-rebuild-checked` | Яркий изумрудный pill-бейдж `Шаг 1 ✕`, `Шаг 2 ✕` | Включён в очередь пересборки. Клик снимает выбор |
| **Ожидает родителя** | `.ln-rebuild-waiting` | Нейтральный серый pill-бейдж `Ждёт` с неактивным квадратиком | Нельзя выбрать, пока не выбран хотя бы один непосредственный родитель слева |
| **Заблокирован (нет данных)** | `.ln-rebuild-blocked`, `.ln-rebuild-no-script` | Красный pill-бейдж `⚠️ Нет данных`, красная пунктирная рамка | Пересборка невозможна: скрипт отсутствует в `public.sql_inventory`. Блокирует выбор потомков |

## 1.4. Нижняя консоль управления (Floating Rebuild Dock)
Закреплена по центру внизу экрана при активном режиме:
* **Сводные счётчики:**
  * `Источников: X`
  * `Выбрано к пересборке: Y`
  * `⚠️ Без скрипта: Z` (отображается только если в ветке есть заблокированные таблицы)
* **Кнопки управления:**
  * **«Выбрать всех потомков»** — автоматически последовательно выбирает все валидные узлы по топологии графа;
  * **«Сбросить»** — полностью очищает выбор и возвращает граф к обычному виду;
  * **«Сформировать SQL пересчёта (Y)»** — открывает модальное окно с готовым SQL-скриптом.

## 1.5. Модальное окно выгрузки SQL
* **Интерактивная очередь выполнения:** список шагов с номерами и полными именами таблиц (`schema.table`) в порядке топологической сортировки.
  * **Безопасное удаление таблиц из очереди:** при наведении курсора на карточку шага, если от данной таблицы не зависят другие оставшиеся в очереди шаги (например, концевые листья в ветках или независимые узлы), отображается кнопка-крестик `✕`.
  * **Защита от нарушения цепочки:** таблицы, от которых зависят последующие шаги в очереди, защищены от удаления (крестик скрыт, при наведении отображается подсказка `Нельзя удалить: от этой таблицы зависят следующие шаги в очереди`).
  * Клик по `✕` удаляет таблицу из очереди, исключает её команды из сформированного SQL, пересчитывает нумерацию шагов, обновляет вкладки баз данных и синхронизирует статус карточки на графе и плавающем доке.
* **Вкладки по базам данных:**
  * Раздельные вкладки для каждой затронутой базы (`БД dds`, `БД dm`). По умолчанию активна первая база из очереди выполнения.
  * Сводная вкладка «Все базы» исключена из-за изолированности подключений в DWH.
* **Скрипт пересборки (для выбранной базы данных):**
  * Скрипт содержит упорядоченную последовательность команд удаления и пересоздания объектов;
  * Блоки SQL-скриптов трансформации для каждого шага:
    * Предварительное безопасное удаление объекта (`DROP TABLE IF EXISTS <schema>.<table>;` / `DROP VIEW IF EXISTS <schema>.<table>;`);
    * Скрипт создания/трансформации из `sql_inventory` с очищенными от префикса базы именами объектов (`core.table`, `ext_ods.table`), включая полный DDL-обвес (PK, UNIQUE, `SET NOT NULL` без дублирования колонок PK, комментарии, индексы и завершающую команду актуализации статистики `ANALYZE <schema>.<table>;`);
    * Оповещение с меткой времени (`DO $$ BEGIN RAISE NOTICE '>>> Таблица ... успешно создана: %', clock_timestamp(); END $$;`);
* **Действия:** «📋 Копировать SQL (БД <db>)» в буфер обмена для активной вкладки.

# 2. Бизнес-правила и ограничения

### 1. Правило последовательного выбора (Downstream constraint)
Чекбокс в таблице-потомке доступен для клика (`canCheckNode`) **только тогда**, когда выполнены оба условия:
1. У таблицы есть скрипт в `sql_inventory` (`hasSqlScript(id) === true`).
2. Все входящие в неё родители из активной ветки пересборки уже готовы:
   * либо являются активным источником `New Data` (`activeSources.has(parent)`);
   * либо уже отмечены пользователем галочкой (`checkedNodes.has(parent)`).

### 2. Правило блокировки узлов без скрипта
Если у таблицы отсутствует SQL-скрипт трансформации в `public.sql_inventory` (`tableInfo.sql_script` пуст):
* Пересборка таблицы в автоматическом режиме невозможна.
* Карточка помечается бейджем `⚠️ Нет скрипта` и замком `🔒`.
* **Ни одна таблица ниже по цепочке (downstream)** не может быть выбрана, так как её родитель не может быть пересобран.

### 3. Каскадный сброс (Cascade uncheck)
Если пользователь снимает галочку с родительской таблицы, запускается функция `cascadeUncheck`:
* Все дочерние таблицы, для которых этот узел был обязательным условием в активной цепочке, автоматически снимаются с выбора.
* Порядок и целостность очереди пересборки гарантированно сохраняются.

### 4. Топологический порядок выполнения (DAG Order)
Нумерация шагов на карточках (`orderMap`) и последовательность скриптов в итоговом файле формируются функцией `getTopologicalRebuildQueue`:
* Опирается на топологический порядок DAG: родительские таблицы всегда выполняются строго раньше дочерних (стейджинг $\to$ детальный слой $\to$ витрины).

### 5. Многобазовая изоляция и Foreign Tables (FDW)
Хранилище данных разделено на физически независимые базы данных: `ods` $\to$ `dds` $\to$ `dm`.
* Межсерверное взаимодействие выполняется через `postgres_fdw`:
  * В базе `dds` настроен сервер `ods_server` (схема `ext_ods` $\to$ удалённая схема `ods.core`).
  * В базе `dm` настроен сервер `dds_server` (схемы `ext_dds` $\to$ `dds.core`, `ext_calc` $\to$ `dds.calc`).
* Все имена объектов в скриптах внутри базы являются двухкомпонентными (`schema.table`), трёхкомпонентные имена (`db.schema.table`) запрещены СУБД.
* **Справочно: работа с Foreign Tables при необходимости**:
  По умолчанию команды обновления Foreign Tables исключены из автоматической генерации скриптов пересборки, так как внешние таблицы создаются разово и статичны при обычных ETL-прогонах.
  Если в DWH изменилась структура колонок или требуется вручную/автоматически пересоздать внешние таблицы, используется следующий эталонный шаблон:
  ```sql
  -- Для БД dds (внешняя таблица из ODS core):
  DROP FOREIGN TABLE IF EXISTS ext_ods.<table_name>;
  IMPORT FOREIGN SCHEMA core LIMIT TO (<table_name>) FROM SERVER ods_server INTO ext_ods;

  -- Для БД dm (внешняя таблица из DDS core):
  DROP FOREIGN TABLE IF EXISTS ext_dds.<table_name>;
  IMPORT FOREIGN SCHEMA core LIMIT TO (<table_name>) FROM SERVER dds_server INTO ext_dds;

  -- Для БД dm (внешняя таблица из DDS calc):
  DROP FOREIGN TABLE IF EXISTS ext_calc.<table_name>;
  IMPORT FOREIGN SCHEMA calc LIMIT TO (<table_name>) FROM SERVER dds_server INTO ext_calc;
  ```
  Логика маппинга серверов и схем:
  - Источник `ods.core` $\to$ таргет БД `dds`, сервер `ods_server`, схема-приёмник `ext_ods`, удалённая схема `core`.
  - Источник `dds.core` $\to$ таргет БД `dm`, сервер `dds_server`, схема-приёмник `ext_dds`, удалённая схема `core`.
  - Источник `dds.calc` $\to$ таргет БД `dm`, сервер `dds_server`, схема-приёмник `ext_calc`, удалённая схема `calc`.

### Граф смежности (`getGraphAdjacency`)
В отличие от SVG-парсинга, граф смежности строится напрямую из метаданных `window.catalogData` для узлов, присутствующих на канвасе:
* `info.lineage.upstream.filter(u => visibleNodes.has(u))`
* `info.lineage.downstream.filter(d => visibleNodes.has(d))`

Это исключает влияние виртуальных транзитных узлов Sugiyama (`vnode-...`) на логику пересборки и гарантирует 100% надёжность определения родителей и потомков.
