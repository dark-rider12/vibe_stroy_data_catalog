# SQL_RULES.md

## Назначение

Документ описывает правила работы с SQL Parsing и SQL Lineage.

SQL Parsing является основой для:

* Table Lineage
* Column Lineage
* поиска зависимостей
* отображения происхождения данных

Ошибки SQL Parsing почти всегда приводят к ошибкам lineage.

---

# Главный принцип

Корректность lineage важнее красоты кода.

Если существует выбор между:

* упрощением парсера
* сохранением корректного lineage

необходимо сохранять корректность lineage.

---

# Источники SQL

Разрешено использовать:

* `public.sql_inventory`
* `pg_views`

Запрещено использовать:

* `pg_stat_statements`

Причина:

`pg_stat_statements` содержит нормализованный SQL и не подходит для построения достоверного lineage.

---

# Что должен поддерживать парсер

Минимально поддерживаемые конструкции:

* SELECT
* INSERT INTO ... SELECT
* CREATE TABLE AS SELECT
* CREATE VIEW AS SELECT
* JOIN
* UNION
* UNION ALL
* WITH (CTE)
* подзапросы

---

# Что считается критичным

Особенно осторожно работать с:

* CTE
* вложенными подзапросами
* алиасами таблиц
* алиасами колонок
* UNION
* многоуровневыми SELECT

Большинство регрессий возникает именно в этих областях.

---

# Алиасы

Алиасы являются частью lineage.

Пример:

```sql
SELECT
    amount AS total_amount
FROM orders
```

Парсер обязан сохранять связь:

```text
orders.amount
    →
total_amount
```

Запрещено терять происхождение колонок из-за алиасов.

---

# CTE

Пример:

```sql
WITH sales AS (
    SELECT *
    FROM orders
)
SELECT *
FROM sales
```

CTE является промежуточным уровнем lineage.

Запрещено:

* игнорировать CTE;
* разрывать цепочку происхождения данных;
* терять зависимости внутри CTE.

---

# UNION

Пример:

```sql
SELECT id FROM table_a

UNION ALL

SELECT id FROM table_b
```

Парсер должен сохранять зависимости от всех источников.

Запрещено учитывать только первую ветку UNION.

---

# JOIN

При JOIN необходимо сохранять:

* происхождение колонок;
* происхождение таблиц;
* связи между источником и результатом.

Запрещено определять происхождение только по имени колонки.

Всегда учитывать таблицу-владелец.

---

# Подзапросы

Пример:

```sql
SELECT *
FROM (
    SELECT *
    FROM orders
) t
```

Подзапрос является отдельным уровнем lineage.

Необходимо сохранять полную цепочку происхождения.

---

# Column Lineage

При работе с колонками:

предпочтение всегда отдаётся точности происхождения данных.

Запрещено:

* угадывать источник колонки;
* использовать эвристики без проверки;
* связывать колонки только по совпадению имени.

---

# Table Lineage

Table Lineage должен строиться на основании реальных зависимостей SQL.

Запрещено:

* создавать искусственные зависимости;
* добавлять связи по шаблонам имен;
* делать предположения без анализа SQL.

---

# Не ломать существующее поведение

Перед изменением парсера необходимо понять:

* какие типы SQL уже поддерживаются;
* какие тестовые сценарии существуют;
* какие кейсы ранее ломались.


---

# Производительность

SQL может содержать:

* большие запросы;
* десятки CTE;
* большое количество JOIN;
* многоуровневые вложения.

Избегать:

* повторного парсинга одного и того же SQL;
* повторных обходов AST без необходимости;
* дублирования промежуточных структур.

---

# Если найден неизвестный SQL

Если встречена конструкция, которую парсер не поддерживает:

Не придумывать поведение самостоятельно.

Не создавать фиктивные зависимости.

Не делать предположения.

Необходимо:

1. Описать ограничение.
2. Показать проблемный SQL.
3. Предложить варианты реализации.
4. Дождаться решения пользователя.

---

# Проверка после изменений

После изменения SQL Parsing необходимо проверить:

* Table Lineage
* Column Lineage
* CTE
* JOIN
* UNION
* подзапросы
* CREATE VIEW
* CREATE TABLE AS

Если изменяется логика происхождения колонок:

дополнительно проверить сложные цепочки Column Lineage.

---

# Зоны повышенного риска

Наиболее рискованные области:

* разрешение алиасов;
* CTE;
* вложенные SELECT;
* UNION;
* происхождение колонок;
* построение Column Lineage.

Любые изменения в этих областях требуют дополнительной проверки.

# Вкладка «Скрипт» и автогенерация DDL

Для таблиц DWH, у которых есть оригинальные SQL-запросы в `public.sql_inventory` или в `pg_views`, во вкладке «Скрипт» отображается исходный код трансформации/создания (плюс дополнительные ограничения, комментарии, индексы и команда `ANALYZE`).

При отсутствии оригинального скрипта трансформации (например, для таблиц-справочников) система автоматически формирует и отображает во вкладке «Скрипт» DDL-код на основе загруженных системных метаданных СУБД:
* Ограничения первичного ключа (`ALTER TABLE ... ADD CONSTRAINT ... PRIMARY KEY`)
* Ограничения уникальности (`ALTER TABLE ... ADD CONSTRAINT ... UNIQUE`)
* Ограничения `NOT NULL` (`ALTER TABLE ... ALTER COLUMN ... SET NOT NULL`):
  * **Исключение колонок PRIMARY KEY:** колонки, входящие в состав первичного ключа, автоматически наделяются свойством `NOT NULL` на уровне СУБД, поэтому они исключаются из блока `SET NOT NULL` во избежание дублирования; если других полей с `notnull` в таблице нет, весь блок `SET NOT NULL` опускается.
* Комментарии к объекту и колонкам (`COMMENT ON TABLE ...` для таблиц, `COMMENT ON VIEW ...` для представлений `type == 'v'`, `COMMENT ON MATERIALIZED VIEW ...` для материализованных представлений `type == 'm'`, `COMMENT ON COLUMN ...` для колонок)
* Индексы (`CREATE INDEX ...`)
* Сбор статистики (`ANALYZE database_name.schema_name.table_name;`):
  * Формируется в самом конце DDL-скрипта для актуализации статистики планировщика запросов после создания/пересборки объектов.
  * Формируется для всех таблиц (регулярных `r`, секционированных `p`, материализованных представлений `m`).
  * Для стандартных представлений (view, `type == 'v'`) команда `ANALYZE` не добавляется, так как в PostgreSQL представления не хранят статистику и вызов команды завершается ошибкой.

Такие DDL-скрипты визуально выделяются в интерфейсе специальным информационным баннером о том, что это системные метаданные, полученные из СУБД.
