# SQL_RULES.md

## Назначение

Документ описывает правила работы с SQL Parsing и SQL Lineage.

SQL Parsing является основой для:

* Table Lineage
* Column Lineage
* поиска зависимостей
* отображения происхождения данных

Ошибки SQL Parsing почти всегда приводят к ошибкам lineage.

---

# Главный принцип

Корректность lineage важнее красоты кода.

Если существует выбор между:

* упрощением парсера
* сохранением корректного lineage

необходимо сохранять корректность lineage.

---

# Источники SQL

Разрешено использовать:

* `public.sql_inventory`
* `pg_views`

Запрещено использовать:

* `pg_stat_statements`

Причина:

`pg_stat_statements` содержит нормализованный SQL и не подходит для построения достоверного lineage.

---

# Что должен поддерживать парсер

Минимально поддерживаемые конструкции:

* SELECT
* INSERT INTO ... SELECT (включая синтаксис с явным списком колонок `INSERT INTO tbl (c1, c2) ...`, где узел `exp.Schema` в `table_lineage.py` автоматически распаковывается в `exp.Table`)
* CREATE TABLE AS SELECT
* CREATE VIEW AS SELECT
* JOIN
* UNION
* UNION ALL
* WITH (CTE)
* подзапросы
* `CROSS JOIN LATERAL` (включая `generate_series`, `unnest` с алиасами `AS col` и `AS gs(col)`)

Не поддерживаются и автоматически отфильтровываются как не имеющие отношения к lineage таблиц:
* `CREATE EXTENSION` / `DROP EXTENSION` (системные команды PostgreSQL отсекаются в `sql_loader.py` быстрым строковым гардом и регулярным выражением перед парсингом AST)
* `DO $$ ... $$` / `DO $tag$ ... $tag$` (анонимные PL/pgSQL-блоки отсекаются перед парсингом AST с защитой регулярных выражений от ReDoS)
* команды управления сессией (`SET ...`)
* команды очистки/удаления таблиц и представлений (`DROP TABLE`, `DROP VIEW`, `TRUNCATE TABLE` — как чисто служебные запросы, так и промежуточные инструкции/преамбулы внутри комплексных скриптов)

---

# Что считается критичным

Особенно осторожно работать с:

* CTE
* вложенными подзапросами
* алиасами таблиц
* алиасами колонок
* UNION
* многоуровневыми SELECT

Большинство регрессий возникает именно в этих областях.

---

# Алиасы

Алиасы являются частью lineage.

Пример:

```sql
SELECT
    amount AS total_amount
FROM orders
```

Парсер обязан сохранять связь:

```text
orders.amount
    →
total_amount
```

Запрещено терять происхождение колонок из-за алиасов.

---

# CTE

Пример:

```sql
WITH sales AS (
    SELECT *
    FROM orders
)
SELECT *
FROM sales
```

CTE является промежуточным уровнем lineage.

Запрещено:

* игнорировать CTE;
* разрывать цепочку происхождения данных;
* терять зависимости внутри CTE.

## Изоляция области видимости алиасов (Scope Isolation)

Псевдонимы таблиц из разных областей видимости (CTE, подзапросы и основной запрос) не должны перезаписывать друг друга.

Пример коллизии:

```sql
WITH cte_12 AS (
    SELECT col_1 FROM db_2.sch_1.tab_6 AS a_2
)
SELECT a_2.col_51 AS col_141
FROM db_2.sch_1.tab_target AS a_1
LEFT JOIN db_2.sch_1.tab_39 AS a_2 ON a_1.col_6 = a_2.col_6
```

Правило в `lineage/column_lineage.py`:

* При сборе маппинга таблиц основного запроса (`alias_mapping`, `cte_alias_to_name`, `branch_alias_map`) и inline-подзапросов (`subquery_map`) таблицы внутри тел CTE обязательно исключаются через проверку `tbl.find_ancestor(exp.CTE) is not None`.
* Внутри каждого CTE карта псевдонимов (`cte_alias_map`) формируется локально для его собственного скоупа (вложенные/чужие CTE исключаются проверкой `cte_ancestor is not None and cte_ancestor is not cte`).
* Запрещено глобально смешивать алиасы таблиц основного запроса и алиасы из тел CTE.

---

# UNION

Пример:

```sql
SELECT id FROM table_a

UNION ALL

SELECT id FROM table_b
```

Парсер должен сохранять зависимости от всех источников.

Запрещено учитывать только первую ветку UNION.

---

# JOIN

При JOIN необходимо сохранять:

* происхождение колонок;
* происхождение таблиц;
* связи между источником и результатом.

Запрещено определять происхождение только по имени колонки.

Всегда учитывать таблицу-владелец.

---

# Подзапросы

Пример:

```sql
SELECT *
FROM (
    SELECT *
    FROM orders
) t
```

Подзапрос является отдельным уровнем lineage.

Необходимо сохранять полную цепочку происхождения.

---

# Column Lineage

При работе с колонками:

предпочтение всегда отдаётся точности происхождения данных.

Запрещено:

* угадывать источник колонки;
* использовать эвристики без проверки;
* связывать колонки только по совпадению имени.

## Двухуровневый fallback сопоставления целевой таблицы и нормализация колонок

* При слиянии результатов в `compute_column_lineage` не допускается молчаливый сброс вычисленных выражений при расхождении формата имени целевой таблицы (например, 2-составное имя `dm.table`, отсутствие схемы или другая схема в скрипте относительно метаданных).
* Если точный ключ `target_table` отсутствует в `lookup`, выполняется двухуровневый fallback-поиск: сначала по `schema.table` (с приоритетом совпадающей БД при неоднозначности), затем по уникальному имени `table` в БД/каталоге. При невозможности сопоставления выводится явное предупреждение `[Column Lineage Warning]`.
* Выражения колонок сохраняются под обоими ключами (нормализованным без кавычек/пробелов и исходным в нижнем регистре), а шаблон `templates/table.html` выполняет поиск с учётом очистки кавычек и пробелов.

## Изоляция баз данных (`dds` ↔ `dm`) и защита вкладки «Скрипт»

* В `attach_sql_scripts` (`generate_catalog.py`) и `compute_column_lineage` (`lineage/column_lineage.py`) при известной `db_name` сопоставление выполняется **строго внутри этой БД** без кросс-базового fallback в одноимённую таблицу другой БД.
* Более свежие версии скриптов (`updated_at DESC NULLS LAST`) не перезаписываются старыми записями; уже заполненные таблицы пропускаются **до** анализа текста.
* `_extract_all_explicit_target_dbs` отклоняет скрипты, явно создающие/загружающие другую БД (`CREATE [UNLOGGED] TABLE/VIEW`, `INSERT INTO`, `SELECT ... INTO`), используя только линейные ($O(N)$) предкомпилированные паттерны `_CREATE_TARGET_RE` и `_INTO_TARGET_RE` с гардом `"INTO" in ...` (квадратичный `SELECT[\s\S]*?INTO` запрещён).

## Раскрытие `LATERAL`-функций (`CROSS JOIN LATERAL generate_series` и др.)

* `_extract_select_lateral_asts` и `_expand_lateral_ast` (`lineage/column_lineage.py`) локально для каждой ветки `exp.Select` раскрывают по AST ссылки на `LATERAL`-функции (`col`, `col.col`, `gs.d`, а также через `SELECT *` в CTE), включая обёртки (`::date`, `CAST`, `COALESCE`) в CTE, `UNION ALL` и прямых `SELECT`, не затрагивая колонки реальных таблиц и литералы.
* В `_resolve_cte_source_column` и AST-fallback в `sources` извлекаются реальные колонки-аргументы функции (либо пустой список для константного диапазона), без ложной привязки к первой таблице ветки.

# Table Lineage

Table Lineage должен строиться на основании реальных зависимостей SQL.

Запрещено:

* создавать искусственные зависимости;
* добавлять связи по шаблонам имен;
* делать предположения без анализа SQL.

---

# Не ломать существующее поведение

Перед изменением парсера необходимо понять:

* какие типы SQL уже поддерживаются;
* какие тестовые сценарии существуют;
* какие кейсы ранее ломались.

# Производительность

SQL может содержать:

* большие запросы;
* десятки CTE;
* большое количество JOIN;
* многоуровневые вложения.

Избегать:

* повторного парсинга одного и того же SQL;
* повторных обходов AST без необходимости;
* дублирования промежуточных структур.

## Оптимизация загрузчика SQL (`sql_loader.py`)

* **Защита от ReDoS (катастрофического возврата):** при удалении многострочных комментариев и разделителей (например, длинных последовательностей `------------------`) регулярные выражения используют линейные паттерны без пересекающихся квантификаторов (замена `(-{2,}[^\n]*\n*)+` на `-{2,}[^\n]*(?:\n|$)`), что предотвращает зависание процесса на скриптах с большим числом дефисов.
* **Быстрые строковые гарды:** перед вызовом тяжёлых регулярных выражений очистки процедурных блоков (`DO $$`) и расширений (`EXTENSION`) выполняется предварительная строковая проверка (`"DO "` / `"EXTENSION"` в тексте запроса).
* **Приоритет актуальных версий:** чтение из `public.sql_inventory` выполняется с сортировкой `ORDER BY updated_at DESC NULLS LAST`, чтобы при наличии нескольких записей для одной таблицы в приоритете обрабатывался наиболее свежий скрипт.

## Оптимизация Column Lineage (`lineage/column_lineage.py`)

* **Многопроцессорная параллелизация (`ProcessPoolExecutor`):** расчёт связей колонок распределяется по всем доступным ядрам CPU (до 16 воркеров). Схема DWH (`MappingSchema`) и справочник колонок инициализируются один раз на каждый рабочий процесс (`_init_column_lineage_worker`), передавая между процессами только компактные структуры данных.
* **Бережная очистка комментариев перед парсингом AST (`_strip_sql_comments`):** перед вызовом `sqlglot.parse_one` (как в `column_lineage.py`, так и в `table_lineage.py`) однострочные (`--`) и вложенные блочные комментарии PostgreSQL (`/* ... /* ... */ ... */`, счётчик `block_comment_depth`), а также осиротевшие маркеры `*/` (например, после `-- /*`) удаляются за один линейный проход ($O(N)$) с быстрым возвратом при отсутствии `--`/`/*`/`*/`. Функция сохраняет `\n`, строковые литералы и dollar-quoted строки (`_DOLLAR_TAG_RE`). При сбое `parse_one` предусмотрен fallback на `sqlglot.parse` для многоинструкционных скриптов.
* **Ранняя фильтрация:** запросы к ручным справочникам `ref_manual_*` (и `ref_source_system`) отсекаются до передачи в парсер `sqlglot`.
* **Безопасный fallback:** при малом количестве запросов ($\le 5$) или системных ограничениях среды расчёт автоматически переключается на однопоточный режим.

# Если найден неизвестный SQL

Если встречена конструкция, которую парсер не поддерживает:

Не придумывать поведение самостоятельно.

Не создавать фиктивные зависимости.

Не делать предположения.

Необходимо:

1. Описать ограничение.
2. Показать проблемный SQL.
3. Предложить варианты реализации.
4. Дождаться решения пользователя.

# Вкладка «Скрипт» и автогенерация DDL

Для таблиц DWH, у которых есть оригинальные SQL-запросы в `public.sql_inventory` или в `pg_views`, во вкладке «Скрипт» отображается исходный код трансформации/создания (плюс дополнительные ограничения, комментарии, индексы и команда `ANALYZE`).

При отсутствии оригинального скрипта трансформации (например, для таблиц-справочников) система автоматически формирует и отображает во вкладке «Скрипт» DDL-код на основе загруженных системных метаданных СУБД:
* Ограничения первичного ключа (`ALTER TABLE ... ADD CONSTRAINT ... PRIMARY KEY`)
* Ограничения уникальности (`ALTER TABLE ... ADD CONSTRAINT ... UNIQUE`)
* Ограничения `NOT NULL` (`ALTER TABLE ... ALTER COLUMN ... SET NOT NULL`):
  * **Исключение колонок PRIMARY KEY:** колонки, входящие в состав первичного ключа, автоматически наделяются свойством `NOT NULL` на уровне СУБД, поэтому они исключаются из блока `SET NOT NULL` во избежание дублирования; если других полей с `notnull` в таблице нет, весь блок `SET NOT NULL` опускается.
* Комментарии к объекту и колонкам (`COMMENT ON TABLE ...` для таблиц, `COMMENT ON VIEW ...` для представлений `type == 'v'`, `COMMENT ON MATERIALIZED VIEW ...` для материализованных представлений `type == 'm'`, `COMMENT ON COLUMN ...` для колонок)
* Индексы (`CREATE INDEX ...`)
* Сбор статистики (`ANALYZE database_name.schema_name.table_name;`):
  * Формируется в самом конце DDL-скрипта для актуализации статистики планировщика запросов после создания/пересборки объектов.
  * Формируется для всех таблиц (регулярных `r`, секционированных `p`, материализованных представлений `m`).
  * Для стандартных представлений (view, `type == 'v'`) команда `ANALYZE` не добавляется, так как в PostgreSQL представления не хранят статистику и вызов команды завершается ошибкой.

Такие DDL-скрипты визуально выделяются в интерфейсе специальным информационным баннером о том, что это системные метаданные, полученные из СУБД.
