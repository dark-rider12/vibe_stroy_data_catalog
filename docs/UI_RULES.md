# UI_RULES.md

## Назначение

Документ описывает правила работы с пользовательским интерфейсом каталога.

Цель изменений UI:

* сохранить существующий пользовательский опыт;
* не нарушать существующую компоновку;
* не ломать адаптивность;
* минимизировать риск регрессий.

---

# Главный принцип

При изменении интерфейса предпочтение всегда отдаётся:

1. сохранению существующего поведения;
2. минимальным изменениям;
3. повторному использованию существующих компонентов.

Запрещено выполнять визуальный редизайн без прямого запроса пользователя.

---

# Не менять без необходимости

Запрещено без явной причины:

* менять структуру страницы;
* менять расположение основных панелей;
* менять навигацию;
* менять размеры основных областей;
* менять существующие UX-сценарии.

---

# Предпочитать существующие решения

Перед созданием нового элемента интерфейса необходимо проверить:

* существует ли аналогичный компонент;
* существует ли аналогичный стиль;
* существует ли аналогичное поведение.

Предпочтительно переиспользовать существующую реализацию.

---

# Работа с CSS

Предпочтительно:

* использовать существующие CSS-классы;
* расширять существующие стили;
* использовать flex-layout и grid-layout.

Избегать:

* дублирования CSS;
* создания почти одинаковых классов;
* хардкода размеров без необходимости.

---

# Position Absolute

Использовать:

```css
position: absolute;
```

только при реальной необходимости.

Перед использованием убедиться, что решение невозможно реализовать через:

* flex;
* grid;
* существующую разметку.

Избыточное использование absolute часто приводит к регрессиям интерфейса.

---

# Размеры элементов

Избегать:

```css
width: 123px;
height: 57px;
```

без необходимости.

Предпочитать:

* flex-grow;
* flex-basis;
* min-width;
* max-width;
* относительные размеры.

---

# Адаптивность

Любое изменение интерфейса должно учитывать:

* большие мониторы;
* стандартные ноутбуки;
* узкие окна браузера.

Запрещено проверять только один размер экрана.

---

# Скроллинг

Перед изменением контейнеров проверить:

* вертикальный скролл;
* горизонтальный скролл;
* поведение длинных списков;
* поведение больших таблиц.

Изменения контейнеров часто приводят к скрытым регрессиям.

---

# Панели и ресайзеры

Особенно осторожно работать с:

* resizer;
* split-view;
* collapsible panels;
* sidebar.

---

# Search Interface

Особенно осторожно работать с:

* строкой поиска;
* поисковыми результатами;
* фильтрами;
* заголовком страницы.

Поиск является критической подсистемой проекта.

---

# Lineage UI

Особенно осторожно работать с:

* масштабированием графа;
* панорамированием;
* выделением узлов;
* focus mode;
* отображением связей.

Перед изменением обязательно ознакомиться с:

```text
docs/LINEAGE_RULES.md
docs/LINEAGE_ARCHITECTURE.md
```

---

# Производительность UI

Избегать:

* лишних перерисовок;
* повторных запросов к DOM;
* повторных вычислений layout;
* создания большого количества обработчиков событий.

Предпочитать:

* кеширование DOM-ссылок;
* делегирование событий;
* локальные обновления интерфейса.

---

# JavaScript

Запрещено:

* переписывать работающие модули без необходимости;
* переносить крупную логику между файлами без запроса;
* менять архитектуру frontend без запроса.

Изменения должны быть локальными и понятными.

---

# Визуальная консистентность

Новые элементы интерфейса должны соответствовать существующему стилю.

Не создавать:

* новые цветовые схемы;
* новые стили кнопок;
* новые варианты отступов;

если аналог уже существует.

---

# Если найдено странное решение

Если в интерфейсе обнаружено решение, которое выглядит избыточным или нелогичным:

Не удалять его автоматически.

Сначала проверить:

* не связано ли оно с исторической регрессией.

Многие "странные" решения существуют для обхода ранее найденных проблем.

---

# Проверка после изменений

После изменения UI обязательно проверить:

* отображение страницы;
* навигацию;
* поиск;
* открытие объектов;
* боковые панели;
* ресайзеры;
* lineage (если затрагивался);
* длинные списки;
* длинные таблицы.

---

# Зоны повышенного риска

Наиболее рискованные области:

* sidebar;
* search header;
* resizer;
* lineage viewer;
* split panels;
* таблицы;
* модальные окна.

Любые изменения в этих областях требуют дополнительной проверки.

# Боковая панель (Sidebar) и дерево объектов `#tree`

## 1. Закреплённый поиск по объектам (DBeaver style)
* **Модуль**: `src/ui/sidebarSearch.js` (`initSidebarSearch`).
* **Контейнер**: `.sidebar-search-sticky`, расположен под кнопкой «Главная страница» и над деревом `#tree`.
* **Sticky-позиционирование**: `position: sticky; top: -20px; z-index: 20` гарантирует, что поле ввода остаётся зафиксированным вверху при скролле длинного дерева объектов вниз.
* **Фильтрация и навигация**:
  * Фильтрует дерево `#tree` по совпадению подстроки в названиях баз, схем и таблиц/представлений без учёта регистра.
  * При совпадении автоматически раскрывает родительские теги `<details open>` и скрывает несовпавшие ветки.
  * При очистке поля (клавиша `Escape` или клик по кнопке `[✕]`) полностью восстанавливает исходное состояние раскрытия всех веток дерева.

## 2. Изоляция названий объектов от браузерного поиска (`Ctrl + F`)
* **Проблема**: Встроенный поиск браузера по странице (Chromium Find-in-Page по `Ctrl + F`) индексирует все физические текстовые узлы DOM. При поиске внутри активной вкладки таблицы (в SQL-скриптах, списке колонок или описаниях) браузер подсвечивал десятки ложных совпадений в боковой панели.
* **Архитектурное решение**:
  Все названия баз данных, схем, групп и таблиц/представлений в `#tree` формируются без текстовых узлов DOM — исключительно через CSS-псевдоэлементы:
  ```html
  <span class="tree-title" data-title="имя_объекта"></span>
  ```
  ```css
  .tree-title {
      display: inline;
  }
  .tree-title::after {
      content: attr(data-title);
  }
  ```
  Chromium TextFinder не индексирует сгенерированное CSS-содержимое (`::after`), благодаря чему поиск `Ctrl + F` остаётся строго внутри активной вкладки и не захватывает боковую панель.
* **Правила для разработчиков**:
  1. **Категорически запрещено** возвращать прямой текст внутрь ссылок `<a>`, `<summary>` или плашек схем `.sidebar-schema-node` внутри дерева `#tree`.
  2. Все новые объекты дерева должны оформляться через `<span class="tree-title" data-title="..."></span>` и атрибут `data-name="..."`.
  3. Для программного чтения имени узла в JavaScript использовать функцию `getNodeText(el)` (`el.querySelector('.tree-title')?.dataset.title || el.dataset.name`), а не `el.textContent`.

## 3. Шапка боковой панели и сворачивание (Collapse mode)
* **Шапка панели**: под логотипом отсутствует текстовый заголовок «Справочник DWH» — блок навигации поднят выше, и список элементов начинается сразу с кнопки «🏠 Главная страница».
* **Кнопка сворачивания/разворачивания (`#sidebarToggleBtn`)**:
  * Имеет высокий приоритет наложения (`z-index: 600`), что гарантирует её видимость и доступность для клика даже при открытом Генераторе шаблонов (шторке).
* **Сворачивание сайдбара (`body.sidebar-collapsed` / `.sidebar.collapsed`)**:
  * Верхняя панель поиска (`.search-header`, `.search-header.compressed`), селектор каталогов и шапка шторки Генератора шаблонов (`.tb-drawer-header`) имеют левый отступ `padding-left: 76px`. Это предотвращает визуальное наезжание плавающих кнопок и элементов управления на кнопку разворачивания сайдбара.

# Экспорт в файл (страница таблицы)

Кнопка «Экспорт в файл» генерирует HTML-файл или, если пользователь передал
`.docx`-шаблон, заполняет его через `docxtemplater` (`src/utils/helpers.js`).

**Имя выходного файла** строится `_buildFileName` (helpers.js:956) из:

1. префикса по типу объекта и **базе данных** (не схеме!): `v`/`m` →
   «Описание вью», база `dm` → «Описание витрины», иначе → «Описание таблицы»;
2. краткого названия `shortName`;
3. суффикса ` (справочник, обновляемый вручную)` для таблиц `core.ref_manual_*`;
4. `_<db>_<schema>_<table>.<ext>`.

Правило выбора «витрины» завязано на `dbName === 'dm'` — одноимённые схемы
в других базах должны получать «Описание таблицы».

**Тег `{file_name}`** в `.docx`-шаблоне (helpers.js:1187,
`fileName2Words = fullFileName.split(' ').slice(0, 2).join(' ')`) заменяется на
**первые два слова** имени файла, например «Описание витрины». Остальные теги:
`{name}`, `{short_rus}`, `{date}`, `{comment_on_table}`, `{rows}`, `{script}`,
`{primary_key}`, `{history}`.
